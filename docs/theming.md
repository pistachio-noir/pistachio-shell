# Theming and colours

The shell publishes Colours to `$XDG_CONFIG_HOME/pistachio/shared-theme` (normally `~/.config/pistachio/shared-theme`), containing `pistachio` or `noir`. Pistachio Text, FM and Notes follow it live. Kitty also follows when its config includes `pistachio-shared.conf`; the shell writes the chosen colours (those of `pistachio-noir.conf` or `noir.conf`) into it, rather than an include, so a kitty.conf that includes one of those files itself gets no "already been included" error, and the publisher reloads running Kitty processes with SIGUSR1.

**Theming integration** (Settings → Appearance → Colours, on by default): the shell sets Kitty, Neovim, VS Code, GTK apps, Vesktop, btop, yazi and zathura up itself to follow Colours. It backs up `kitty.conf` / `init.lua`, adds its line at the end, marked (Kitty: a `# pistachio-shell theming…` comment line above a plain `include pistachio-shared.conf`; Neovim: a line ending in `-- pistachio-shell theming`) and copies the theme files in. An app that already has its own theme is asked about in Settings first (Keep mine / Use Pistachio). Turning the switch off removes only those marked lines, so the app's own settings apply again. Neovim needs an `init.lua` (not `init.vim`). Text, FM and Notes follow Colours either way.

Neovim can follow the same choice with the files in `integrations/neovim`: its existing Pistachio Noir colourscheme has a matching Noir palette, and `pistachio-shared.lua` checks the shared choice while Neovim is open. `integrations/neovim/install.sh` installs these into the matching Neovim config and backs up the current init and colourscheme; it expects the existing `vim.cmd("colorscheme pistachio-noir")` line. The fallback is Pistachio when the shared file is absent. In Noir its code keeps a few muted colours so syntax stays readable; the editor itself stays grey.

**VS Code** (since 21 November 2026) is the third app under Theming integration. Its theme is an extension, `integrations/vscode/pistachio-noir` (Pistachio Noir and Noir, the shell's palettes), which psc packages as a `.vsix` and installs with VS Code's own `code --install-extension`, so VS Code records it (a folder copied into `~/.vscode/extensions` by hand never shows up in the theme list). The shell then sets one line in `~/.config/Code/User/settings.json`, first in the file, marked with a block comment:

```jsonc
    "workbench.colorTheme": "Pistachio Noir" /* pistachio-shell theming */,
```

Every other byte of `settings.json` (comments, order, trailing commas) stays as you wrote it, and VS Code applies the change at once, so switching Colours recolours VS Code within a second. A theme you picked yourself is replaced only after you agree (the "Use Pistachio" question); the marker then keeps your old one (`(was "…")`), and switching Theming integration off puts it back, or removes the line if there was none. `settings.json` is backed up beside itself before the first change. VSCodium and Code - OSS are handled the same way (their own settings and extension folders). If VS Code follows the system's light/dark setting (`window.autoDetectColorScheme`), the row says so and nothing changes. The extension stays installed when you switch off; pick it by hand any time (Ctrl+K Ctrl+T).

Hyprland’s active window and group borders follow the shell’s Colours setting live: pistachio in Pistachio Noir, light grey in Noir; inactive borders stay transparent. Applied at runtime and after Hyprland reloads.

Settings → Appearance → Monochrome wallpaper optionally desaturates the desktop wallpaper and its live switcher preview while Noir is selected (off by default). The desktop cat keeps its selected coat colours in both schemes. Switching back restores the original colours; wallpaper files are never modified.

Settings → Experimental → OLED black (since 22 November 2026, off by default) darkens the shell while Colours is Noir (it doesn't apply to Pistachio Noir): a true black background and darker surfaces, text and accents. With Theming integration on, Kitty, Neovim and VS Code follow it as OLED Noir: the shell runs `psc theme oled`, which writes `noir` to `~/.config/pistachio/shared-theme` (older Text and FM builds read exactly that, so they stay on plain Noir) and a marker file `~/.config/pistachio/shared-oled` beside it. Text and FM (since 22 November 2026) read the marker too and turn OLED Noir live. Kitty gets `oled-noir.conf`, Neovim's colourscheme reads the marker (a running Neovim switches within a second; a Neovim set up by an older psc gets its colour files refreshed on the next switch, the old ones kept as backups), and VS Code's theme line becomes "OLED Noir" (the extension is installed again first when its copy is out of date). The Kitty and VS Code files are made from the Noir ones by `tools/make-oled-themes.py`: run it again after changing either.

## GTK, Vesktop, btop, yazi and zathura (since 28 November 2026)

Five more apps under the same switch, each with the same rules: an app with its own theme is asked about first, its config is backed up beside itself (`….pistachio-bak-<date>`) before a change, and switching off removes only what the shell added. Their theme files are made from `src/Theme.qml` by `tools/make-app-themes.py` (into `integrations/gtk`, `btop`, `yazi`, `zathura` and `vesktop`, three schemes each) and built into psc; run the tool again after changing a tone, and `python3 -B tools/make-app-themes.py --check` (in `tests/run.sh`) says when a file is out of date.

| App | What the shell writes | A switch |
| --- | --- | --- |
| GTK 4 / libadwaita | `~/.config/gtk-4.0/gtk.css` starts with a marked `@import url("pistachio-shared.css");`, the colours beside it as CSS variables (`--window-bg-color`…; libadwaita 1.6+ no longer reads `@define-color`) | restart an app |
| GTK 3 | the same in `~/.config/gtk-3.0/`, as `@define-color` names, and the `adw-gtk3-dark` theme (`gsettings … gtk-theme`, needs `x11-themes/adw-gtk3`; the old theme name is kept in the marker and put back by undo) | restart an app |
| Vesktop | a marked block at the end of Vencord's QuickCSS (`~/.config/vesktop/settings/quickCss.css`), Discord's colour variables; written in place, as Vencord watches that file | at once |
| btop | `color_theme = "pistachio-shell"` in `btop.conf`, the theme in `btop/themes/pistachio-shell.theme` (its first line keeps your old theme's name) | at once (SIGUSR2) |
| yazi | `~/.config/yazi/theme.toml` picks the flavor `flavors/pistachio-shell.yazi` (with a `tmtheme.xml` for code previews) in dark and light | restart yazi |
| zathura | `zathurarc` ends with a marked `include pistachio-shared` (`set default-bg …`), so its colours win | at once (D-Bus `SourceConfig`) |

"Use Pistachio" over a GTK or yazi config with colours of its own moves that file aside whole (`gtk.css.pistachio-own`, `theme.toml.pistachio-own`) and switching off puts it back, followed by anything you added after the shell's lines. A GTK theme picked in gsettings other than Adwaita or adw-gtk3 counts as your own. In btop the theme name itself says it's ours (btop rewrites its whole config, comments and all, after a change made in btop). A Vencord theme of your own (`enabledThemes`, `themeLinks`) is asked about; with QuickCSS off in Vencord's settings, the row says to turn it on. zathura's recolour mode (Ctrl+R) uses the shell's background and text.
